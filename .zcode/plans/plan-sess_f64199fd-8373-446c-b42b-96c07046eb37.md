# Plan — Data Pipeline piloté depuis l'UI (vue Données = centre de contrôle)

## Objectif
Éliminer tout hardcoding des workers. La vue Données devient le **centre de contrôle** : choix des assets, timeframes, profondeur d'historique. Import CSV générique (pas seulement MT5). Workers lisent la config depuis la DB à chaque cycle.

## Architecture

```
Vue Données (UI)  ←→  Settings → Assets (UI)
        │                      │
        ▼                      ▼
  table configuration    table assets (source column)
  (worker_*)             (binance|ig, actif)
        │                      │
        ▼                      ▼
  Worker Bybit WS        Worker IG
  (lit config + assets   (lit config + assets
   à chaque reconnect)    à chaque cycle 30s)
```

## Partie 1 — Backend : Workers dynamiques

### 1.1 Ajouter 2 colonnes à la table `assets`
Migration `00XX_worker_config.sql` :
```sql
ALTER TABLE assets ADD COLUMN symbol_bybit TEXT;  -- ex: 'BTCUSDT', 'XAUUSDT'
ALTER TABLE assets ADD COLUMN epic_ig TEXT;       -- ex: 'CS.D.EURUSD.CFD.IP'
-- + config worker dans la table configuration (clés worker_*)
```
Pré-remplir pour les assets existants.

### 1.2 Clés de configuration worker (table `configuration` existant)
- `worker_timeframes` → `["M5","M15","H1","D1"]` (JSON)
- `worker_historique_mois` → `"6"`
- `worker_actif_bybit` → `"1"` / `"0"`
- `worker_actif_ig` → `"1"` / `"0"`

### 1.3 Modifier `data/src/bybit_ws.rs`
- Supprimer `SYMBOLES`, `INTERVALS`, `bybit_vers_asset()` hardcodés
- Dans `session_unique()` : lire `SELECT id, symbol_bybit FROM assets WHERE source='binance' AND actif=1 AND symbol_bybit IS NOT NULL`
- Lire `worker_timeframes` depuis `configuration`
- Construire les topics dynamiquement
- Si la liste change → forcer un reconnect (détection par hash de la liste d'assets, vérifié toutes les 30s)

### 1.4 Modifier `data/src/ig_worker.rs`
- Supprimer `ASSETS_IG` hardcodé
- Dans `boucle_worker()` : à chaque cycle (30s), lire `SELECT id, epic_ig FROM assets WHERE source='ig' AND actif=1 AND epic_ig IS NOT NULL`
- Lire `worker_timeframes` depuis `configuration`
- Changer `prochaines` de `Vec` fixe → `HashMap<(String, String), Instant>` (clé = asset×tf)
- Adapter le pacing et le budget à la liste dynamique

### 1.5 Toggle ON/OFF des workers
- Les workers vérifient `worker_actif_bybit` / `worker_actif_ig` à chaque cycle
- Si `"0"` → sleep et skip (pas de fetch/stream)
- Si `"1"` → reprendre normalement

## Partie 2 — Backend : Import CSV générique

### 2.1 Nouveau handler `data/src/../api/src/data_csv_handlers.rs`
Endpoint `POST /api/data/import-csv` :
- **Multipart** file upload (pas de scan de dossier)
- Form fields : `file` (CSV), `asset` (ex: "NAS100"), `timeframe` (ex: "M15")
- Format CSV accepté : `timestamp,open,high,low,close,volume` avec :
  - Délimiteur auto-détecté (`,` ou `;`)
  - Timestamp auto-détecté : Unix secondes (10 chiffres), Unix millisecondes (13 chiffres → /1000), ou date ISO (`2026-01-15 10:30:00`)
  - Skip header row si présente (détection : première ligne non-numérique)
- Insert : `inserer_bougies_avec_source(asset, tf, bougies, "csv")`
- Réponse : `{ total_lues, total_inserees, asset, timeframe }`

### 2.2 Supprimer/rétrograder l'ancien handler MT5
- Garder `POST /api/data/import-mt5` comme alias (rétro-compatibilité) mais marquer déprécié
- Ou supprimer complètement (remplacé par le CSV générique)

## Partie 3 — Backend : Nouvelles API endpoints

### 3.1 `GET /api/worker/config`
Retourne :
```json
{
  "timeframes": ["M5","M15","H1","D1"],
  "historique_mois": 6,
  "actif_bybit": true,
  "actif_ig": true
}
```

### 3.2 `PUT /api/worker/config`
Body : `{ timeframes?: string[], historique_mois?: number, actif_bybit?: bool, actif_ig?: bool }`
Écrit dans la table `configuration`.

### 3.3 `GET /api/worker/status`
Retourne :
```json
{
  "bybit": { "actif": true, "connecte": true, "assets_count": 3, "derniere_bougie": 1786701420 },
  "ig": { "actif": true, "connecte": false, "assets_count": 2, "erreur": "quota" }
}
```

### 3.4 `GET /api/worker/assets`
Retourne les assets avec leur config worker :
```json
[
  { "id": "BTC", "source": "binance", "symbol_bybit": "BTCUSDT", "actif": true },
  { "id": "DAX", "source": "ig", "epic_ig": "IX.D.DAX.IFD.IP", "actif": true }
]
```

## Partie 4 — Frontend : Vue Données redessinée

### 4.1 Section 1 : Contrôle des workers (en haut)
```
┌─────────────────────────────────────────────────────────┐
│  📦 Pipeline de données    [▶/⏸ Bybit] [▶/⏸ IG]       │
│  Statut : ● Bybit WS (3 assets, connecté)              │
│           ● IG (2 assets, en attente quota)             │
├─────────────────────────────────────────────────────────┤
│  Timeframes actifs : [M5 ✓] [M15 ✓] [H1 ✓] [D1 ✓]    │
│  Historique : [6 mois ▼]                                │
└─────────────────────────────────────────────────────────┘
```
- Toggle Bybit/IG ON/OFF → `PUT /api/worker/config`
- Checkboxes TF → `PUT /api/worker/config`
- Dropdown historique → `PUT /api/worker/config`
- Statut workers → poll `GET /api/worker/status` toutes les 30s

### 4.2 Section 2 : Gestion des assets (synchronisée)
```
┌─────────────────────────────────────────────────────────┐
│  Assets du pipeline (synchronisés avec Paramètres)     │
│  [X] BTC (Bybit)  [X] XAUUSD (Bybit)  [X] DAX (IG)   │
│  [X] XAGUSD (Bybit)  [X] NAS100 (IG)                  │
└─────────────────────────────────────────────────────────┘
```
- Cases à cocher = toggle actif/inactif (même logique que Settings)
- Utilise le même `assets.store` (Pinia partagé)
- Badge de la source (Bybit/IG) affiché à côté de chaque asset

### 4.3 Section 3 : Import CSV
```
┌─────────────────────────────────────────────────────────┐
│  📥 Importer données CSV                                │
│  [Glisser un fichier .csv ici ou cliquer]               │
│  Asset : [NAS100 ▼]   Timeframe : [M15 ▼]             │
│  Format : timestamp,open,high,low,close,volume         │
│  [📥 Importer]                                          │
│  ✅ 12 400 bougies insérées (NAS100 M15)               │
└─────────────────────────────────────────────────────────┘
```
- Upload multipart → `POST /api/data/import-csv`
- Dropdowns asset/TF
- Feedback succès/erreur

### 4.4 Section 4 : Couverture DB (existante, améliorée)
- Table existante (asset × TF × bougies × depuis × jusqu'à × statut)
- Ajouter colonne "Source" (bybit_ws / ig_worker / csv / mt5)
- Auto-refresh toutes les 60s (pas seulement au chargement)

### 4.5 Synchronisation Settings ↔ Données
- Settings → Assets (GestionAssets) utilise déjà le store partagé
- Data view → mêmes cases à cocher, même store
- Un changement dans l'un est visible dans l'autre immédiatement (Pinia réactif)

## Partie 5 — Ce qui est supprimé

| Supprimé | Remplacé par |
|----------|-------------|
| `SYMBOLES` hardcodé (bybit_ws.rs) | Lecture `assets.symbol_bybit` |
| `INTERVALS` hardcodé (bybit_ws.rs) | Lecture `worker_timeframes` config |
| `ASSETS_IG` hardcodé (ig_worker.rs) | Lecture `assets.epic_ig` |
| `TIMEFRAMES_IG` hardcodé | Lecture `worker_timeframes` config |
| `bybit_vers_asset()` match | Mapping via `symbol_bybit` column |
| Scan dossier MT5 | Upload CSV multipart |
| Bouton "Lancer la collecte" (one-shot) | Workers persistants pilotés ON/OFF |

## Ordre d'exécution

1. Migration DB (colonnes `symbol_bybit`, `epic_ig` + pré-remplissage + clés config)
2. Workers dynamiques (bybit_ws + ig_worker lisent depuis DB)
3. Endpoints worker (GET/PUT config, GET status, GET assets)
4. Import CSV générique (multipart upload)
5. Frontend vue Données (redesign complet)
6. Tests + build

## Tests
- Migration : `cargo test -p db` (nouvelles colonnes lisibles)
- Workers : tests unitaires sur la lecture dynamique (mock DB avec assets variés)
- CSV : tests sur le parsing (formats de timestamps, délimiteurs, headers)
- Frontend : `npm run build` (type-check)
- Intégration : vérifier que cocher/décocher un asset modifie le comportement du worker au cycle suivant
